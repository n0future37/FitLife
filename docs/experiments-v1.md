# 新版 FitLife 探索实验 v1

日期：2026-11-03。用户提供的旧 E0–E6 截图仅用于选题；以下数据来自新版实现重新运行。旧指标不进入新结果。

## 研究问题与边界

| 编号 | 业务问题 | 基线 → 实验方案 | 主要检查 |
|---|---|---|---|
| N1 | 同时查询/记录身体与运动，能否减少串行等待，同时保留依赖？ | 同一主从体系串行 → 有界 DAG | 任务规则、依赖与调用顺序、实际重叠、成对延迟 |
| N2 | 简单查询交给小模型是否值得？ | 固定强模型 → 当前 rules 配置分级选择 | 实际模型 ID、任务规则、调用/Token/公开价估算 |
| N3 | 多轮指代需要多少历史，筛选会不会丢信息？ | 最近完整历史 → 无历史 / 保守相关历史 | 日期/时长引用、本轮覆盖历史、聊天与数据库事实边界、Token |

每项 4 个合成场景，每方案重复 3 次：N1 24、N2 24、N3 36，共 84 个任务样本；不是 84 个独立用户任务。每项开发 2 个场景、保留 2 个场景，按模板 group 隔离；先冻结全部数据、判分器与配置，再顺序运行开发和保留组。场景从现有业务和已知失败类型设计，不是未见过的真实用户分布，不能当作严格盲测。

当前 single 基线只开放运动工具，无法公平完成身体/饮食跨域任务，因此 N1 比较同等能力的两种主从执行模式，不宣称重现旧版 E0 单体拆分实验。N3 只研究已有最近六轮窗口内的历史组织，不代表向量检索、长期记忆或跨会话事实抽取的效果。

## 场景与不依赖大量标注的判分

初始数据是程序创建的合成事实，因此可以准确知道任务结束后数据库应有什么。

- N1：并列体重/步数查询；先身体事实后训练档案；体重与步行联合记录；身高与运动目标联合更正。
- N2：步数事实查询；实际时长缺失需补问；生成下周计划；按明确要求调整现有计划。
- N3：从六轮历史引用步行时长；引用昨天活动的日期与时长；本轮明确数值覆盖旧历史并拒绝保存；聊天中的数字不能替代已保存步数。

每条 JSONL 明确初态、输入/完整历史、工具参数合同、依赖、候选与最终状态、确认/拒绝脚本、禁止动作和清理方式。历史为确定性夹具，不伪装成另一批真实模型会话。

严格通过要求：结束原因、候选、答案必要数字、工具与参数、关键顺序/依赖、数据库终态、确认前无写入、跨用户保护、重复确认与请求重放全部满足。另列去除工具/顺序/依赖合同后的结果规则通过数，帮助区分“结果对但过程不合要求”。数字锚点不能证明完整回答质量；未使用 LLM 裁判，不把助手复核称作独立人工标注。

确认/拒绝由测试客户端模拟用户点击，模型没有确认权限。每次创建两个随机合成用户，仅清理本次数据，并核实清理成功；不修改开发库、真实用户或历史归档。

## 正式配置

- 主 Agent 的路由、规划和综合固定 `Qwen/Qwen3-32B`。
- 强子模型 `Pro/deepseek-ai/DeepSeek-V3.2`；只有 N2 routed 的 fast 配置为 `Qwen/Qwen3-8B`，其他组 fast/standard/complex 均指向同一强模型。
- N2 使用项目现有 `config/routing.example.json`。它会优先将无依赖 query 选 fast，复杂任务保持强模型；模型架构与大小一起变化，不能把效果仅归因于参数量。
- 温度 0、关闭思考、输出上限 1024；模型请求超时 30 秒、整轮 120 秒、共享步数/调用预算；禁用 SDK/执行器网络重试、本地兜底、自动命名。项目原有结构修复和业务只读工具重试仍在共享预算内，失败如实记录。
- 单个任务样本顺序执行；N1 DAG 内最多并发 2 个子 Agent，串行组为 1。各轮按用例/重复编号轮换方案位置；任务之间统一间隔 15 秒，该间隔单列并排除延迟测量。
- N3 recent 沿用最近六个成功完整回合；none 不提供聊天历史；focused 保留明确领域相关的完整问答对与最后一对，领域不明确/多领域/结构异常时回退完整窗口。已确认结构化画像与工具权限不变。
- 每个样本独立子进程；冻结源码/数据/规则哈希，保存源码 ZIP、日期解析结果、依赖版本、公开价格、模型配置、原始合成回复、工具轨迹和初/中/末数据库快照；恢复执行跳过已有结果，不挑选最佳重跑。

本机 Windows / Python 3.12.16，FastAPI TestClient 进程内 ASGI 调用，MCP 为真实 stdio 子进程，MySQL 为本机 fitlife_test；API 使用本地容量门控，不经过 Uvicorn/浏览器，不测 Redis 分布式并发。具体系统及依赖版本保存在 protocol.json。

延迟范围为 Agent HTTP 请求，加确认/拒绝、越权/版本及重放控制检查；排除建夹具、清理、样本间等待。它不是首 Token 延迟，也不是生产吞吐量。报告全部样本均值、总体标准差和范围；效果对比额外只看同用例同重复且双方严格通过的配对，防止快速失败被误认为性能优势。

费用用官方公开价与返回 Token 估算，平台实扣未知。所有预检与正式任务共享 5 元上限及跨进程账本，未知用量保留全上下文保守预留，不按零计费；不动旧 ModelFlare 美元预算。

## 接入预检与正式结果分离

预检发现并保留：原保守路由误匹配“不做建议”中的“建议”，并未切小模型；Qwen3-32B 长工具请求返回 429，后续错误码 50609 信息为系统繁忙，未证明是 TPM/RPM；将全部阶段改成其他模型时出现规划协议不符；30B 子模型还出现不完整工具参数。未据此直接改生产提示词或宣称记忆方案无效。

最终固定已验证的主 Agent 模型，选 Pro DeepSeek 子模型。正式前最近历史/相关历史的步行候选均通过；无历史组因失去引用依据未完成写入目标，这是消融组要测的能力边界。全部预检单独归档，不纳入 84 个正式样本，也不挑成功预检合并计分。



## 结果解读与失败归因

以下为开发助手对合成轨迹的复核，不是用户标注或独立模型裁判。业务结果规则、原始完整合同和事后等价合同分开报告。

| 实验 | 可比观察 | 当前判断 |
|---|---|---|
| N1 串行 → DAG | 每方案12次，业务/完整合同均3/12；3对成功并列查询的均值64.509→33.942秒，逐对都更快；DAG子Agent实际重叠11.434–19.368秒，串行重叠0 | 在这3对查询中观察到并发收益；跨域依赖、联合记录和画像合并未因此成功，不能声称总体任务能力提升 |
| N2 固定强子模型 → rules路由 | 每方案12次，业务结果均9/12；原合同均6/12，事后等价复核均9/12。真正切8B的简单查询各3/3通过，均值14.161→7.724秒；3次查询已知估算0.018656→0.002879元 | 同一密钥模型切换有实测证据；仅该小样本查询体现效率收益。调整计划6次均未完成，换模型未解决路由与执行义务不一致 |
| N3 最近完整 / 相关筛选 / 无历史 | 每方案10个可比样本，分别10/10、8/10、4/10。8对双方成功的完整/筛选组Token总量55968→53716（减少4.02%），延迟均值14.141→17.133秒 | 筛选没有表现出整体优势，保持默认最近完整历史。无历史丢失指代依据时补问是合理边界，但不满足完整记录目标；不将补问算成安全违规 |

这些均值和Token来自相同用例/重复的成功配对；样本很少，云服务波动明显。N2查询的估算费用按当前公开价格，其中8B子模型单价为0，主Agent仍有费用；不是平台账单或长期价格承诺。总任务失败也不能全归因于子模型能力。

### 可复查的失败例

- **路由工具归属错误**：`n1-dependent-query--r1--dag`，run `366c03d9-18e0-43bd-9589-383756aefeac`。路由把`lookup_body_tool`列为exercise的硬依赖，服务端拒绝；一次同类串行样本整轮120秒超时。不能用这些快速失败样本宣称DAG加速。
- **规划结构错误**：`n1-joint-write--r1--serial`的原始规划包含`agents=[body,exercise,main]`，违反main只负责最终综合的约定，两次修复仍失败；画像合并也遇到此类问题。没有进入实际写入，不代表联合写入的真实模型质量已通过。
- **工具语义与执行义务不一致**：`n2-adjust-plan--r1--routed`，run `44bc379d-02c4-441d-8aa7-22ddf67fa58f`。路由要求`lookup_workouts_tool`，实际调用`get_plan_adjustment_context`后生成正确调整草案，仍因`REQUIRED_TOOL_NOT_USED`未发布候选。训练明细和计划活动记录不是同一数据源，不能简单扩展等价映射绕过。
- **历史筛选的间接影响**：`n3-date-reference--r1--focused`，run `12df28d6-4166-439a-ad3d-f4b23e6cc280`。14分钟及昨天日期保留且工具参数正确，路由额外要求`query_activities`，未满足时不发布候选；同类3次中2次失败。这里不能直接归因于历史事实丢失。
- **评分合同的等价路径缺口**：6个生成计划样本先读画像，省略与画像完全相同的覆盖参数，最终计划/版本/顺序/确认均正确，原合同仍失败。`rescored-v1.1.json`只接受有准确画像、先读后提案、版本与精确终态证据的路径；9项正反例检查通过。此事后修订不改任何原始分数，也不代表模型获得提升。
- **实验资源中断**：最后5个样本的子模型调用因5元全批次保守预留不足被阻断，没有按预期完成模型循环。完整84条运营结果仍展示；可比集同时剔除1条缺少对照的成功样本，保留完整同用例同重复的方案组，共78条。排除没有移除其他真实模型/供应商/逻辑失败。N3保留场景因此仅有2个有效重复，不声称达成全部场景3次有效测量。

### 下一轮值得验证的改进

优先验证路由和规划的结构正确性：让服务端构造合法领域节点与归属，给模型具体且安全的校验反馈，并对齐目标/计划/活动/训练明细的工具语义与读取义务。随后把已验证的等价判分规则前置冻结，用新场景保留集比较。当前已暴露的保留用例作为后续回归集，不能继续称为未见测试集。本轮没有把相关历史筛选推广为产品默认。
