# 同能力单Agent与多Agent架构对照

完成日期：2026-11-04。统一单Agent覆盖三领域43工具后，再进行本次对照。正式批次 `99bc5e84-c55b-49b0-8810-b322a0ad5521`，六个已见合成场景，各架构三次，共36条，18组配对。原运动single的10工具基线没有作为对手。

本批多Agent严格合同通过数比统一单Agent少2条。 原始多Agent失败中有1条受本地实验预算预留影响，不能全部归因为架构任务能力；下面单列资源匹配描述和双方补测。 性能和费用需看下方同一成功子集，不能直接用失败更快的总体均值下结论。本实验比较两套可运行架构整体，不证明Agent数量本身具有因果优势。

## 实现与控制变量

- unified：一个工具循环处理身体、饮食、运动，连续收集最多3候选；不调用意图路由、规划和子Agent。master：领域清单、依赖规划、子Agent工具循环、证据综合。
- 两边共用SQL业务工具、用户资源归属、参数校验、候选合并、事务确认、版本/摘要与幂等机制。明确步行录入两边都会收窄为4工具；其他任务unified可见完整目录，子Agent可见领域视图。两边都支持独立只读工具的有界并发，并非只有多Agent能并行。
- 所有模型阶段同用Pro/deepseek-ai/DeepSeek-V3.2、温度0、思考关闭、输出1024；单次60秒、整轮240秒、模型网络重试0，SDK重试关闭；全轮步数16/模型尝试12/工具调用12/输入单次150000字节/总token预算单位350000，并发上限2。工具只读重试保持默认1，写工具不自动重试。
- 关闭模型选择、本地兜底、自动命名、历史筛选；本组会话历史为空，计划场景有明确初态画像与计划。每个样本独立进程，顺序执行、两组位置轮换，样本间30秒冷却不计延迟。真实云模型＋进程内ASGI TestClient＋真实stdio MCP/MySQL测试库；未测浏览器TTFT、Redis分布式负载或生产吞吐。
- 子Agent每领域提出一个候选后可以结束；统一Agent需处理完全部要求后结束。提示词、工具视图、协调与停止规则都是整体架构差异。进一步隔离Agent数量本身，需要新增单Agent工具裁剪等消融，本轮没有实施。
