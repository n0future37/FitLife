# 后端性能验证与限制

日期：2026-11-18。真实HTTP、MySQL和Redis，固定模型与合成用户；不是模型质量评测。

## 机制修复

- 显式设置TCP_NODELAY，覆盖Python 3.12继承socket协议编号为0时未自动设置的分支。
- 客户端闲置连接2秒、服务端5秒，保留复用边界余量，不添加HTTP应用层重试掩盖失败。
- 同步数据库请求在进入认证/业务线程前异步排队，每进程按数据库池大小限制为5；超时503。异步Agent和上传继续独立管理容量，健康检查不参与排队。
- 认证将令牌与用户存在性合并查询，保留格式、有效期、撤销及归属校验，不做认证缓存。

## 最新针对性对照

4vCPU、标称4GB的Linux主机，应用2进程共2CPU/1024MiB，MySQL8.4.13占1CPU，Redis7.4.12；同机发压器1CPU/512MiB。真实Docker内网TCP，不包含公网、模型耗时。每轮32用户/3200活动，安全检查另保存1条；每轮独立清理。C1每场景12秒，C32完整写入30秒，每设置3次交错重复。

下表比较已有数据库准入与加入认证查询优化；每项为三次档位均值。

共33档、60,191次计时业务操作、88,802次HTTP，业务错误0；确认写入28,812条与实际新增一致（含预热）。权限、摘要、32次并发重复确认、重放和Agent容量机制另验收。固定Agent容量测试中的预期429不混入计时业务错误。

活动分页未见改善；写入P99三次范围由339.597–613.892ms变为336.187–483.499ms，仍有反向样本。三次短测不证明稳定SLA、生产最大QPS或统计显著性。两个工作进程的长连接分配不均、进程内排队和CPU忙碌均可能影响尾部；现有证据未精确拆分全部因素。没有提高硬件配额、延长超时、取消事务或放宽确认规则换取指标。

## 数据与复现

脱敏的全部33档聚合与范围见[机器可读结果](../benchmarks/results/backend-20261118.json)。原始逐请求、失败尝试、资源与源码快照保留在本机，未随公开仓库分发；当前仓库提供最终修复及合成发压脚本，不冒充所有历史中间镜像均已公开。

在全新专用测试环境按[压测运行说明](../benchmarks/cloud/README.md)准备服务；不要连接自己的开发库或真实用户库。单档核心命令：

```sh
python benchmarks/cloud/load.py --workers 2 --concurrencies 1 --seconds 12 --repeats 3 --skip-agent-capacity
python benchmarks/cloud/load.py --workers 2 --scenarios propose_confirm --concurrencies 32 --seconds 30 --repeats 3 --skip-agent-capacity
```

两个命令均需在专用Compose的load服务中运行，并使用不同产物目录记录条件；脚本会检查专用测试库与合成数据。每次业务写入包含提出、确认两次HTTP，不能与单请求读取吞吐混为一谈。
