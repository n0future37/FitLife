# 三领域统一单Agent

新增模式为 `unified`。它与默认 `master` 使用相同的业务服务和当前用户资源，覆盖身体、饮食、运动的43个工具；原来的 `single` 仍保留为运动10工具历史基线，不能拿它直接与三领域主从比较。

| 模式 | 如何理解请求和选择工具 | 候选与保存 |
|---|---|---|
| single | 原运动单Agent | 保留原行为与回归 |
| unified | 一个工具循环处理全部领域；不调用意图路由器、规划模型或子Agent | 连续收集最多3项候选，结束后由可信程序统一形成待确认操作 |
| master | 主清单/领域绑定/依赖规划，分发给领域子Agent | 子Agent返回候选，主编排统一形成待确认操作 |

三个模式都受到已有业务规则和接口范围约束。“43个工具全集”不代表任意自然语言请求都能成功，也不代表新增了医学诊断、精确视频计数等未完成能力。图片和视频继续使用已有公共媒体服务，本次架构对照只测文字任务。

## unified的一次跨域请求

例如“记录今天体重70公斤、步行20分钟，并新增给定标签食物”：

1. 一个Agent看到本轮原文、相同会话历史、可信日期和三领域工具目录。
2. 它可连续提出身体、运动、饮食工具调用。模型只能提出操作，不能确认。
3. 工具使用既有校验和归属规则返回结构化候选；候选先暂存在本轮内存列表，反馈candidate_collected，模型继续完成其余任务。
4. 相同规范化候选重复提出时不追加第二项；实际调用仍计入调用次数和预算。
5. 模型结束本轮后，可信程序检查失败状态，将候选交给与master共用的合并/持久化路径。兼容画像补丁合并，冲突则要求澄清。
6. 待确认操作落入MySQL后，用户对具体版本和摘要确认，业务服务在同一事务保存全部操作。重复确认和请求重放复用现有机制。

如果流程在临时候选落库前退出，业务事实未写入；重试可能重新调用模型。如果待确认操作已经持久化，API可以恢复它。这里没有承诺模型服务只计费一次或支持任意工具步骤的持久检查点。

查询仍通过工具读取当前用户事实；已知输入错误可更正，重复无效参数受到执行器限制。失败的事实检索不能被当作“无记录”，未完成检索时不生成整份可确认写入候选。

## 公平对照的含义

两种架构使用相同业务服务、资源归属、事务确认、幂等与数据模型；整体工具能力一致。差异包括领域提示词、工具视图、任务拆分、证据传递、执行调度与停止规则。

unified通常看到完整目录；明确单纯步行录入时，两种架构都使用已有的4工具收窄规则。两种执行器都能并行调用独立只读工具，且有并发上限；并行并不是多Agent专属能力。

master每个领域通常在提出一项候选后结束该子任务；unified需要继续处理剩余要求，最后结束整个循环。因此本次比较是两套可运行架构的整体比较，不能把任何效果全部归因于“Agent数量”。可靠确认和跨用户隔离是共用服务端能力，也不能冒充多Agent独有收益。

## 本机选择模式

在准备好现有开发库凭据、令牌和SILI_API_KEY的终端中：

```powershell
Set-Location H:\Tomorrow\FitLife
$env:FITLIFE_ORCHESTRATION = 'unified'
& .\scripts\start_siliconflow.ps1
```

停止当前服务后，将环境变量设为 `master` 并重新启动即可切回主从模式。该选择对服务进程生效；本轮没有自动重启已有网页服务，也没有改变默认master配置。

日常启动的模型配置和实验配置分别管理。实验会把所有决策阶段设置为同一个型号，并关闭模型路由、本地备用和自动命名，避免把模型强弱或额外命名调用混进架构对照。

## 验证与边界

当前新增实现已完成Windows集中回归，并覆盖三领域联合确认/拒绝、查询、画像合并、重复工具候选、请求重放、跨用户确认和禁止模型自行确认。固定模型回归验证执行机制，真实模型效果以独立架构实验报告为准。

最新源码尚未上传、运行新云CI或重新验收Linux镜像；旧Linux/云CI结果只属于对应源码时点。实际个人贡献需在项目复盘后确认。
