# 画像与运动记录：业务服务模块

## 职责与数据流

画像保存已确认的目标/偏好/可用日/频次/时长，活动保存实际发生的项目、日期和分钟数。
画像按字段合并并记录来源/更新时间/版本；本步只有walking、gentle_mobility，暂不包含力量组次或饮食。

受信任用户身份 → 校验输入 → 产生待确认操作 → 用户检查内容 → 确认/拒绝/修改 → 事务保存 → 本人查询。
生成候选只写待确认表，不改画像或活动。confirm/reject/revise供可信交互入口调用，不给模型确认权限。
业务服务独立于模型/MCP；现由认证API注入Actor，并经私有MCP提供查询/候选工具。模型和客户端不能指定Actor身份，确认不暴露给模型。

| 对象 | 表 | 作用 |
| --- | --- | --- |
| 内部用户 | fl_users | 资源所属主体；不是登录/密码系统 |
| 画像 | fl_profiles | 结构化值、逐字段来源、版本和更新时间 |
| 活动 | fl_activities | 本人实际活动，唯一source_action_id防同操作重复写入 |
| 待确认操作 | fl_pending_actions | 内容、摘要、版本、有效期、状态、幂等请求标识及结果 |

代码：database.py是连接和ORM；business.py是参数契约和业务事务；migrations是独立版本迁移；
db_check.py负责测试库迁移/验收及合成数据清理。本模块同步数据库I/O，每个操作/并发任务独立Session。
将来接异步API时需用工作线程或迁移AsyncSession，不能把同步SQL直接阻塞事件循环。

## 为什么这样实现

- 调用方为每个请求生成并复用request_key，同用户/同种操作的重复请求返回原候选；内容不同报冲突。
- 确认必须携带action_id、revision、digest，服务端检查归属、状态、内容摘要和15分钟有效期。
  摘要用于绑定内容，不能代替身份认证；数据库不信任模型声称“用户已确认”。
- 修改候选递增revision并重算摘要，旧确认报STALE_CONFIRMATION；已拒绝/过期不可继续写入。
- 画像候选绑定原画像版本；其他变更先保存后，旧候选变为superseded，不能覆盖最新画像。
- 每次写入先锁本用户行，再处理候选和业务记录。状态applied与业务数据在同一事务提交，
  中途异常一起回滚。重复确认读取原结果；数据库还以唯一约束阻止同候选生成两条活动。
- 这是先保证正确性的保守锁粒度：同用户写入串行，跨用户可独立进行。后续高并发时根据测量再细化。
- MySQL DATETIME本步存整秒UTC，日期按上海当天；摘要使用同一时间精度，避免落库截断后摘要失配。
