# FitLife 项目理解入口

2026-11-17最新：[Agent简历专项复习路线](learning-roadmap.md)，以Agent v1.3五条为准。只讲Agent所需模块与必要执行边界，从“记录今天步行二十分钟”开始；不另开完整后端或视觉算法课程。

本页说明当前实现，技术事实以源码与 `readiness-v1.md` 的核查证据为准。旧 Fit 的实验不作为新版成果；功能实现、模型效果、个人贡献分别核实。

## 为谁解决什么问题

FitLife 面向希望持续记录运动和习惯的个人。用户无需记住表单位置，可以用自然语言维护偏好、提出计划、记录实际活动和查看进度。模型负责理解与工具选择；数据库事实、数值计算、权限和保存规则由服务端负责。饮食和身体记录是关联领域，应用提供一般管理辅助，不作医疗结论。

最典型任务是“记录今天步行二十分钟”。它的输入是当前用户、会话、原始请求、请求编号和服务端日期；最终输出是可核对的候选、确认后的活动记录，以及可重放的执行结果。

## 一次请求如何完成

1. 页面带个人令牌和幂等编号提交请求。后端校验身份与会话归属，登记本轮运行；用户身份不由模型参数决定。
2. 主 Agent 的意图清单识别这是运动领域的活动录入。服务端校验领域和工具依赖；单纯步行记录只提供相关工具，缺少实际分钟数就补问，不能从计划或偏好猜测。
3. 运动子 Agent 在工具循环中选择 `propose_activity`，提交项目、实际分钟数和日期。工具通过 MCP 调用业务服务，校验参数和归属，只提出候选。
4. 主 Agent 收集子 Agent 的候选，形成统一待确认操作。页面明确显示“尚未保存”。涉及多个领域时可组成整份变更，不能只成功一半。
5. 用户确认具体候选版本和摘要；服务端重新核对状态、版本和归属，在事务中保存。重复确认返回已有结果，不再插入第二条记录。拒绝、修改要求、来源变化或过期使旧确认失效。
6. 再问“今天完成了多少”，查询工具读取已确认事实；记录、回答和数据库应一致。运行 ID、工具顺序、模型信息、耗时和错误用于排查与评测，私有轨迹脱敏。

这条链路的关键价值是把“模型提出操作”和“服务端可靠执行”连接起来，而不是只生成一句听起来成功的回答。

## 主从 Agent 如何分工

主 Agent 按“意图清单 → 服务端绑定 → 依赖规划 → 子任务执行 → 综合”工作，可以用 Plan-and-Solve 风格描述。单领域直接执行对应子任务，不必再调用一次规划与综合模型。多领域才需要依赖图及综合。

身体、饮食、运动子 Agent 使用有界的 ReAct 风格工具循环：选择工具、接收真实结果、继续调用或回答。这里的“推理”指可观测的决策和工具轨迹，不声称保存模型隐藏思维链。步数、实际活动、训练明细是不同业务事实，不能互相替代。

子 Agent 不直接互发消息。主 Agent 维护依赖关系，把前序工具的结构化观察传给后续任务，包含来源、查询范围和成功/失败状态；独立任务可有界并行。MCP 是子 Agent 调用业务工具的协议，不等于 Agent 之间的消息系统。前序失败不能被解释为“无记录”。

## 模型路由与可靠性

意图路由回答“交给哪个领域、需要哪些依赖”；模型路由回答“本任务使用哪个配置”。配置分别描述平台、协议、模型、凭据和能力，多个同平台模型可以共用一把密钥。实际能否切换仍由平台账号和模型权限决定。

日常配置采用保守规则：简单且无历史的明确只读任务可以选小模型；复杂、写入或依赖任务保留强模型。超时、有限重试、熔断、全轮预算和结束原因都由执行器控制。本机小模型仅承担已验收的文字只读兜底，不接管高风险写入，不承诺零故障。多模态使用独立能力配置。

路由不是必然更快或更省。已有完整实模实验在成功配对子集中观察到 Token 和延迟上升，简历需要保留这个结果及原因，不能只挑有利样本。

## 记忆和上下文是什么

当前请求是本轮原文，优先于历史偏好。会话近期历史用于解释指代；结构化画像是已确认、可更正和忘记的偏好；临时约束带作用日期；计划与活动属于业务事实；待确认操作、运行和租约保存执行状态。它们有不同更新规则，不能全部当作一段聊天摘要。

MySQL 保存权威事实和持久状态；Redis 用于必要的容量控制、租约等。最近历史、按任务筛选或不使用历史是已做过对照的上下文策略。当前默认不能根据单次成功实验随意替换。知识检索是已有出处资料的关键词基线，没有在主业务链路接入向量检索、重排或 Milvus 长期记忆。

## 如何测试与评估

普通软件测试验证业务规则、权限、事务、版本、幂等和恢复。固定模型响应再配合真实 MCP/MySQL 检查执行器和工具契约，这类通过率不等于真实模型理解能力。

真实模型评测从固定初态执行用户任务，检查最终事实、工具参数与顺序、确认前是否写入、越权和重复写入；同时记录耗时、Token、尝试次数和费用估算。每个用例有清理规则，开发与保留按模板组划分。已经用于修复的场景属于已见回归，不能再称盲测。开放回答的完整语义质量尚无独立评分证据。

N1 比较串行与 DAG；N2 比较固定强模型与规则模型选择；N3 比较历史上下文策略。原始失败、未知费用与旧源码快照保留。定向修复复验不能替换完整测试集的历史分数。

## 简历与面试的事实边界

可以围绕主从编排、模型适配、工具权限、确认幂等、结构化记忆、持久恢复和可复现评测组织项目。数字只引用明确批次和条件；不用“全面提升”“零故障”“生产级”代替证据。

实现中大量代码由助手协作完成。个人负责的设计、实验、排查与理解程度需要逐项复盘后确认，再选择简历动词。当前项目文件存在、测试通过，并不能直接证明个人独立完成或已经掌握。

建议复习顺序：业务与一次请求 → 主从编排与工具 → 可靠写入与恢复 → 记忆与模型路由 → 评测及失败分析。每个模块先讲完整输入输出和设计理由，再准备一段准确的项目表述与少量追问答案。
